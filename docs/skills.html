Skills, triggers & refusals

Four skills, one dispatcher. What fires each one — and, just as deliberately, what each one refuses to do.

The refusals are not incidental; they are where spec-flow's principles live. amend never edits silently, close never sets a completed Linear state and never archives an unmet contract, start never implements, implement never auto-closes. Each is called out below.

start /spec-flow start <goal>

Open a contract for a new code change. Drafts only. On a Linear host, moves the ticket to Contract Review once the body is written.

Triggers when

  • /spec-flow start <goal>.
  • "let's spec-flow this" / "open a contract for X".
  • A non-trivial change where you want a contract first.

Does NOT invoke for

  • Trivial changes (5-line bugfix, type fix, one-file glue) — contracts are opt-in.
  • Multi-feature roadmaps — single-change-scoped.
  • Resuming/implementing an existing contract — that's implement.

Refuses to: proceed to implementation (ends by telling you to run /spec-flow implement); silently pick a host in the ambiguous "reference" case (asks once); connect the Linear MCP for you. Note: on the Linear host it overwrites the existing description by default — it prepends instead only when you explicitly ask to preserve the text.

implement /spec-flow implement [name]

Start or resume coding against an active contract. First-run and resumption are one flow; behavior differs on observed git state, not a stored flag. On a Linear host, moves the ticket to In Progress before writing code. Before declaring the work done, it dispatches the contract-verifier agent to verify each Done when bullet by running the change (not by reading the diff).

Triggers when

  • /spec-flow implement [name].
  • "let's start coding on X", "pick up the okta-auth contract".
  • Resuming a contract from a prior session.

Does NOT invoke for

  • Drafting a new contract — that's start.
  • Closing a finished change — that's close.
  • Code work with no associated contract.

Refuses to: auto-close (prompts you to run /spec-flow close once scope ships and the Done-when checks pass); declare done on the strength of the diff — the contract-verifier agent must observe each Done when bullet by running the change first; work outside the contract's Out of scope — a tempting addition must go through amend; silently edit the contract — divergence routes through amend; persist the cadence choice (re-negotiated every session).

amend Skill(spec-flow:amend) — usually called from within implement

Propose a contract edit mid-implementation. The contract is an agreement; both parties must agree to changes — this is the load-bearing rule.

Triggers when

  • Approach turned out wrong; switching.
  • A new constraint surfaced (library limit, pattern conflict, perf).
  • An Out of scope item now needs to be in scope (or vice versa).
  • An Open question was resolved and should be promoted to Approach.
  • You ask: "update the contract to reflect X".

Does NOT invoke for

  • Trivial implementation details (variable names, helper choices, file layout).
  • Final state at close — that's close's migration step.

Refuses to: ever edit the contract silently — it summarizes the drift, shows a before/after scoped to the affected section, and waits for explicit sign-off ("Apply this amendment?"). "No" leaves the contract unchanged. It also refuses to restructure the whole contract — amendments are narrow, touching only the drifting section, and preserve every untouched section (critical on Linear, whose API replaces the full description).

close /spec-flow close [name]

End an active contract by migrating durable findings to the durable layer, then archiving. Closing implies completion. On a Linear host, advances the ticket to a review state (body left intact) — never to Done. The Done when gate reuses implement's verify result or dispatches the contract-verifier agent itself.

Triggers when

  • /spec-flow close [name].
  • "this change is done", "archive the X contract", "wrap up the okta-auth work".

Does NOT invoke for

  • A mid-implementation pause — the contract just stays active.
  • Abandoning an unfinished change — close means completion; abandonment is a manual move/delete.
  • A contract that never had implementation work — suggests re-evaluating first.

Refuses to: silently archive an unmet contract — the Done when gate halts on any unmet bullet and asks (close as known gap / amend to a narrower done / pause); migrate silently — every ndr atom and README edit is proposed, then applied only after sign-off; set a completed Linear state (it advances to a review state but leaves Done for you at merge); edit the ticket body (the contract stays in the description for retrospective); auto-run the optional drift check; delete anything (file is archived, not deleted; ticket is preserved).

Migration targets: architectural choices → ndr atoms via Skill(ndr:capture-decision); user-facing changes → README via librarian. Out-of-scope items, resolved-but-artifactless open questions, and conversation history are explicitly not migrated.

The contract-verifier agent

spec-flow now ships its first agent. It is a read-and-execute verifier: given the contract's Done when bullets and a change scope, it runs each bullet — exercising the relevant test, command, or endpoint — and returns a per-bullet verdict (met / not_met / drifted / unverifiable) with evidence. It is deliberately adversarial: a bullet is not_met until the outcome is positively observed, because "looks done in the diff" is exactly the drift it exists to catch. It never edits source, commits, or runs destructive commands.

It is dispatched in isolated context — independent of the implementer's view — by implement (before declaring done) and reused or re-dispatched by close (the Done when gate). If unavailable, both skills fall back to running the checks inline.

The /spec-flow dispatcher

The command itself is a thin router. It parses the first argument as a subcommand and invokes the matching skill.

InvocationRoutes to
/spec-flow start <goal>Skill(spec-flow:start) with the goal text
/spec-flow implement [name]Skill(spec-flow:implement) — infers from active .docs/ contracts if name omitted
/spec-flow close [name]Skill(spec-flow:close) — infers from active contracts if omitted
no subcommandlists active .docs/ contracts and asks which action + which contract
unknown subcommandlists the three valid subcommands and asks you to retry

Note: amend has no dedicated subcommand — it is invoked from within implement (or directly via Skill(spec-flow:amend)) when reality diverges. The README also mentions a resume verb for picking work back up; in the shipped command, resumption is handled by implement, which treats first-run and resumption as the same flow.

The refusals at a glance

SkillThe line it won't cross
startwon't implement; won't silently pick a host; overwrites the Linear body by default (prepends only if you ask to preserve it)
implementwon't auto-close; won't declare done without the contract-verifier agent observing each Done when bullet; won't work outside Out of scope; won't silently edit the contract
amendwon't edit the contract without sign-off; won't restructure beyond the drifting section
closewon't archive an unmet contract silently; won't migrate without sign-off; won't set a completed Linear state or edit the ticket body (advances to a review state only)
all fourwon't connect the Linear MCP for you — surfaces the gap and waits
