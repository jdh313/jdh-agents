Validation

The rules that keep atoms well-formed are enforced twice on the way in: a soft pre-flight an agent runs on in-memory drafts, and a hard gate the write script enforces at disk. They overlap on purpose.

Validation in NDR is defense in depth. The soft layer catches problems early — before a draft is even a file — and gives actionable feedback an LLM can fix. The hard layer assumes nothing about what came before it and refuses to write anything malformed, because it is the last thing standing between a draft and the vault. A check appearing in both is not redundancy; it's the soft layer saving a round trip and the hard layer guaranteeing the invariant.

persist.py exit codes — the failure contract mechanics

The write path validates all drafts before writing any, then performs writes transactionally. Its exit code tells the orchestrator exactly how to respond:

ExitMeaningOrchestrator response
0successparse written / superseded / aliases_moved for the summary
1validation (taxonomy, missing field, bad JSON)surface errors, loop back to drafting
2supersession conflictstop — needs manual resolution
3mid-transaction half-statesurface the half_state so the user repairs by hand

No silent partial writes: a supersession that fails halfway reports which slugs moved and which atoms were patched, then exits 3.

A third gate, on the read side

The two gates above live in the plugin (Python). There is a second implementation — the standalone ndr repo — and it enforces the same atom shape at a different moment: when an atom is read. Its parse pipeline is fence-split → YAML → Zod, and the Zod FrontmatterSchema is the gate:

// ndr · src/domain/schema.ts (excerpt)
export const FrontmatterSchema = z.object({
  id:            z.string().regex(/^\d{4}$/),   // quoted 4-digit; "0128" not 128
  title:         z.string().min(1),
  status:        z.enum(["current","superseded","retracted"]),
  decision_date: IsoDate,
  project:       Wikilink,
  supersedes:    z.array(Wikilink),             // REQUIRED present (no default)
  superseded_by: z.array(Wikilink).default([]),
  area:          z.string().min(1),
  topic:         z.string().min(1),
  reversibility: z.enum(["easy","medium","hard"]),
  // ... aliases, derived_from, informed_by, impacts, revisit_triggers, tags
});

This is why a malformed atom can be caught even if it somehow reached disk unvalidated: the reader rejects it on the way out. Corpus-wide read verbs (ndr search, ndr current) skip a malformed atom with a warning rather than aborting the whole query; a targeted ndr resolve <id> still throws, because you asked for that specific atom.

The fork — two implementations, honestly

The mechanics live in two places, and they are not the same code.

  • Plugin (Python). scripts/persist.py is the live write enforcement today — the capture pipeline pipes drafts to it and it owns ID assignment, the taxonomy gate, and the supersession transaction.
  • Standalone ndr (TypeScript). Its read side is complete — ndr resolve / search / lineage / current, with the Zod schema above as the read-time gate. Its write verb, ndr capture, is explicitly "a later slice" — not built yet.

So right now: writes are validated by persist.py; reads (in the standalone CLI) are validated by Zod. When ndr capture lands, the write gate is expected to move into the TypeScript domain layer alongside the schema. Until then, treat persist.py as authoritative for what actually gets written, and schema.ts as authoritative for the canonical field contract.

Where the two definitions differ today

They agree on the field set, the enums, and "supersedes: must be present." Two divergences worth knowing:

Rulepersist.py (write)schema.ts (read)Reading of it
Alias formatmust start with ndr-generic kebab-case (^[a-z0-9][a-z0-9-]*$)persist.py is stricter. An atom written by the plugin always satisfies Zod; a hand-authored kebab alias without ndr- would pass Zod but be refused by persist.py.
Taxonomyvalidated against on-disk .taxonomy/*.yamlarea/topic only checked non-emptyTaxonomy membership is a write-time concern; the read schema treats them as free strings.

Neither is "wrong" — they enforce at different moments for different reasons. The honest summary: the field contract is shared; the membership and namespace rules are enforced by the write path. If you're hand-editing an atom, satisfy persist.py's rules, since it's the stricter of the two.

Real atoms carry harmless variance the schema tolerates field note

Reading actual vault atoms, you'll see frontmatter that isn't byte-identical to the template — e.g. id: "0005" (double-quoted) vs id: '0007' (single-quoted), older atoms with extra date_created: / date_modified: keys from an Obsidian plugin, or atoms predating the aliases: field entirely. The YAML→Zod pipeline accepts these: quoting style is irrelevant once parsed, unknown extra keys are ignored, and absent optional fields fall back to their defaults (aliases: [], etc.). What it will not tolerate is an unquoted id: 0128 (parses as the integer 128 and fails the /^\d{4}$/ string regex) — which is exactly why the schema comment insists the id be quoted.

Validation isn't only on the way in

Two more agents check invariants the write/read gates can't see, because they span multiple atoms:

  • ndr-curator — corpus health: bidirectional chain integrity, orphaned supersession, alias drift (one slug on two current atoms), taxonomy violations, missing fields. Read-only by default; --fix repairs only missing back-pointers.
  • ndr-drift-auditor — coherence against code: does the implementation still match what the current heads claim? (See Lifecycle.)

So the full picture is four checkpoints: soft pre-flight (per draft) → hard write (per draft, at disk) → read schema (per atom, on resolve) → corpus audit (cross-atom, on demand). Shape is judged where judgment helps; invariants are enforced where they must hold.
