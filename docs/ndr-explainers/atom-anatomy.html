Atom anatomy

One decision per file. YAML frontmatter the machine reads; a hybrid-altitude body a human scans. Atomicity is what makes everything downstream work.

A decision atom is a single markdown file under ~/Loose Ends/Decisions/, named <id>-<kebab-title>.md (e.g. 0007-mvp-substrate-markdown.md). It has two parts: a frontmatter block that carries identity, lineage, and classification as queryable fields, and a body that records the decision and its reasoning at graduated levels of detail. Nothing else lives in the file — assumptions, alternatives, and consequences all fold into the body's altitude structure.

Why assumptions live in the body, not frontmatter design note

Each assumption is a small structured record — a description, a current-state, and a "revisit if" condition. Obsidian's Properties UI is flat: nested objects don't render and Bases can't filter on inner fields. So assumptions live in the body as > [!warning]- <slug> callouts (description paragraph + Current state: / Revisit if: bullets), with a backtick-separated slug list at the top of ## Assumptions giving enough surface for "which assumptions does this rest on?" without expanding any. Human-readable and skill-parseable, without pretending to be a query target it can't be.

The hybrid-altitude body

The body is not free prose. Every section is heading + a one-line gist (always visible) plus an optional collapsed callout for deeper texture. A reader scanning the atom sees only headings and gist lines; drilling down is one click per altitude. The trailing - on [!info]- / [!warning]- is what makes Obsidian render the callout collapsed — the artifact itself declares "this is supplementary," so the reader doesn't curate altitude on every read.

The atomicity rule

One chosen path, one set of consequences, per file. "Use FastAPI and Postgres" is two atoms. "Use FastAPI because it's async and we already have Postgres" is one atom — Postgres is context for the choice, not a co-decision. The capture pipeline splits bundles before drafting, and the reviewer fails any draft that smuggles two choices into one body.

Atomicity is not a style preference — it is what makes the supersession primitive work. This is recorded in the corpus itself, atom 0008:

Why atomicity is load-bearing from 0008-decisions-atomic

Once "use FastAPI + Postgres" lives in one file, revising just the Postgres half breaks the supersession primitive — you can't cleanly supersede half a file. Bundled decisions can't supersede per-part. The grouping that bundling would have given you is carried instead by cross-decision edges (informed_by:, area:, topic:) — let structure emerge from the corpus rather than be flattened into one document.

Consequence: the capture skill MUST split bundled candidates into N atoms; relationships live in lineage fields, not shared documents.

So the whole file format earns its keep only because each file holds exactly one revisable decision. That sets up the next page.
