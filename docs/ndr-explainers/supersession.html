Supersession

A decision is never edited to mean something new. When the call changes, a new atom supersedes the old one — and every read walks the chain to the current head.

This is the idea the whole system is built around. Without it, NDR is a folder of markdown notes. With it, decision history is a linked, append-only ledger where "what's current" is always one walk away and "what was true then" is never destroyed.

The primitive: declare what you replace

A revising decision must declare supersedes: [[Decisions/<old>]] in its frontmatter. That single declaration drives a small transaction the write path performs atomically — the predecessor is flipped and back-linked in the same operation that writes the successor. There is no "edit the old file later" step that could be forgotten.

The link is bidirectional: supersedes: on the new atom, superseded_by: on the old. Forward links let a reader who lands on an old atom walk to the head; backward links let an audit confirm the chain is intact from either end.

The single biggest failure mode of this system: reading a stale starting atom directly. A ticket body, a code comment, or your own memory hands you ndr:0070. You Read the file. It confidently states the opposite of current policy — because it was true on 2026-05-18. Nothing about the file warns you it's three revisions deep unless you check superseded_by: and follow it. This is why the read skills refuse to Read atom files directly, even when you already know the exact ID.

The reference grains — naming intent at write-time

References are bi-temporal. Sometimes you mean "the atom that justified this code back then" (historical); sometimes "the decision that governs this code now" (live). Forcing one reference form to do both jobs is exactly what makes ADR-NNNN-style links rot on supersession. NDR's ndr: scheme has three grains so the writer names intent and the reader resolves the right atom(s):

FormExampleResolves toUse when
atom-idndr:0070that exact atom, frozendocumenting why something was built — a historical anchor
slugndr:#substrate-shapethe atom currently holding that alias — follows supersessioncurrent governance matters; you want the live atom
topicndr:substrate/substrateall current atoms in that area/topicthe whole area governs the call site

The slug grain is why aliases move during supersession: ndr:#substrate-shape keeps resolving to the head because the slug is handed from predecessor to successor in the same transaction. The link text never changes; its target follows the chain.

Where the walk lives, and the guard rails around it mechanics
  • One walker. Both read skills (/decisions, /ground) are thin; the supersession walk lives in a single worker, ndr-reader (Stage 3). Keeping the walk in one place is why it can't drift between entry points.
  • Cycle guard. If a chain revisits an already-seen ID, the walker records the cycle and stops rather than looping forever.
  • Convergence. Multiple search hits in one lineage dedupe to a single head.
  • Multi-supersession is manual. If a predecessor is already superseded by a different successor, the write path refuses — almost always two competing successors drafted in parallel, which a human must reconcile.
  • Atomicity is the precondition. A bundled decision can't supersede per-part. The walk only stays clean because each atom holds exactly one decision (see Atom anatomy).

Why not just edit the old file?

Because the old reasoning is data. Atom 0102 is in the corpus precisely because it records a reversal — the assumptions behind 0070 weakened, so the head flipped back toward markdown. If the rule were "only capture forward progress" or "edit in place," that flip would be invisible, and the chain head would lie about how the system actually came to its current state. Supersession exists to record the change without rewriting history. The stale atoms aren't clutter; they're the audit trail.
