Lifecycle

Two halves. Capture turns a conversation into atoms on disk; reading turns a question into the current head. Each half is a thin skill plus focused workers, with exactly one component allowed to touch disk.

skill — scope & user interaction subagent — isolated, focused work persist.py — the only write path

Capture: /capture-decision

The skill is a thin orchestrator. It detects what the conversation is about and talks to the user; the composing, judging, and writing are delegated. No draft reaches disk until the reviewer passes and the user accepts — there is no draft status, drafts live in memory.

Why the work is split this way design rationale
  • Skill owns scope + interaction. The conversation is already in context; "what is this about?" stays local to avoid token/latency cost of shipping it to a subagent.
  • Subagents have one job each, in isolation. The reviewer cannot rewrite the draft; the drafter cannot write to disk. Failure stays contained.
  • persist.py is deterministic. ID assignment, taxonomy enforcement, and the supersession transaction must not depend on LLM judgment — it's plain, tested code, and the only path to disk.

Reading: /decisions, /ground, /drift-check

Three entry points, two workers. /decisions and /ground both dispatch the same supersession-walking reader; /drift-check dispatches a different worker that compares heads against code. The skills stay thin so the walk to head lives in exactly one place — that's what keeps it from drifting between entry points.

Drift resolutions land back in capture

A /drift-check divergence is never auto-applied. The human picks one of three, and two of them re-enter the capture flow above:

  • Amend — narrow the atom: draft a successor with supersedes: [original] that refines scope. → /capture-decision
  • Supersede — replace it wholesale: a successor with supersedes: [original]. → /capture-decision
  • Revert — the code drifted, not the decision: change the code back. → a follow-up edit

In NDR, "amend" and "supersede" both materialize as a new atom that supersedes the original — the difference is only how much of the decision the successor revises. There is no in-place edit of a decision's substance; the chain is the record.

Grounding is opt-in per repo. A repo joins the NDR-tracked set by pasting a snippet into its .claude/CLAUDE.md that names it as tracked and tells the orchestrator to /ground before substantive code work. Editing CLAUDE.md is the commitment; repos without coverage get no vault noise.
