Nested Decision Records

How engineering decisions get captured as atomic markdown, revised through supersession, and read back without going stale.

NDR is a personal-discipline system for recording engineering decisions as atomic markdown artifacts in an Obsidian vault, with explicit lineage and supersession-aware reading. The point is not "write decisions down" — plenty of tools do that. The point is that when a decision is revised, the revision is structurally linked to what it replaced, and every read walks that link to the current head. Cross-session decision drift becomes visible by construction instead of discoverable in hindsight.

This set documents how that works and — more importantly — why the supersession discipline is the load-bearing idea. If you only read one page, read Supersession.

The system at a glance

NDR is split into three layers, each with one job. A thin skill owns conversation scope and user interaction; focused subagents compose and judge atoms in isolated context; a deterministic script is the only thing that touches disk. The same split runs in reverse on the read side.

Why this shape

  • Skill = scope + interaction. The conversation context is already loaded, so "what is this about?" stays in the skill — sending it to a subagent costs tokens and latency.
  • Subagents = focused composition in isolated context. The reviewer can't accidentally rewrite a draft; the drafter can't accidentally touch disk; the reader can't write at all.
  • persist.py = determinism. ID assignment, taxonomy enforcement, and the supersession transaction must not depend on LLM judgment. It is plain code, tested in isolation, the only path to disk.

The four user-facing skills

SkillSideWhat it does
/capture-decisionwriteScan a chat for atomic decisions, confirm with the user, draft → review → persist. Refuses to write a revising decision without supersedes:.
/decisions <topic>readUser has a topic or ndr: ref in hand → walk supersession to the head → return a brief.
/ground [scope]readBefore substantive code work: infer scope, surface the heads that govern this area, hand ndr: refs to a coding subagent.
/drift-check [scope]auditCompare current decision heads against a code diff; surface divergences with three resolutions each — amend, supersede, revert.
One thing to know before the Validation page. There are two implementations in play. The Claude Code plugin (skills + agents + persist.py, Python) is what runs the live capture workflow today. The standalone ~/Projects/ndr repo is a TypeScript reimplementation whose read side is complete (ndr resolve / search / lineage / current) but whose write verb (ndr capture) is still a future slice. They agree on the atom shape; they enforce it at different points. The Validation page keeps them distinct rather than blurring them.

The one idea that matters

A decision is never edited in place to mean something new. When the call changes, you write a new atom that declares supersedes: [old], and the system patches the old atom's superseded_by: back-pointer in the same operation. The old atom stays on disk, frozen, honest about what was true then. Reading resolves forward along that chain to whatever is current now.

The failure mode this prevents — and the single biggest way to misuse NDR — is reading a stale starting atom directly. A ticket cites ndr:0070; you open 0070; it says "swamp is canonical." But 0070 was superseded twice. The head says the opposite. Every read path exists to walk that chain for you. Why this matters →
