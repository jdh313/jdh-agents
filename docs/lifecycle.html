The contract lifecycle

One change moves through three explicit, user-triggered phases. Nothing advances on its own.

A contract is opened, worked against, and closed. Implementation can loop back through amend whenever reality diverges from what was agreed. Each transition is a deliberate user action — spec-flow never auto-advances, never auto-closes, and never edits the contract silently.

Phase 1 — start draft only

Opens a contract for a new change. Drafts only; it explicitly does not begin coding.

  1. Detect host — .docs/ file vs. existing Linear ticket, from the goal text. See the two hosts.
  2. Flag other active contracts — lists open .docs/*.md; a visibility nudge, not a gate.
  3. Gather context proactively — reads CLAUDE.md, searches the code, pulls library docs via Context7, checks the installed dep version, scans relevant ndr atoms, reads project rules. (Linear host: reads the existing ticket body as drafting input.)
  4. Converse only where uncertain — surfaces findings, then asks targeted questions only where the path isn't clear. Proposes defaults rather than open-ended "what do you want?". May suggest forking into the debate skill, or /grill-with-docs if vocabulary is contested.
  5. Draft the six-section contract from the template.
  6. Confirm & write to the chosen host after the user approves. (Linear host: overwrites the existing ticket description by default — it prepends above the original text only when the user explicitly asked to preserve it.)
  7. Move to Contract Review linear only — once the body is written, advances the ticket to the Contract Review state (resolved by name via list_issue_statuses; skipped with a note if the team has no such state). File host has no status.
  8. End — tells the user to run /spec-flow implement when ready. Stops there.

Phase 2 — implement first run = resumption

Starts or resumes coding against an active contract. First-run and resumption share one flow — behavior differs on observed state (VCS history, working tree), never on a stored flag.

  1. Identify target & detect host — from the argument's shape, or by scanning active .docs/ contracts.
  2. Read the contract and follow any linked ndr atoms.
  3. Assess state — detects the VCS first (.jj/ present → prefer jj log / jj st over git; under jj, git status misreads the working copy). Surveys recent commits, uncommitted changes, files touched. Summarizes in 2–3 lines as either "no work yet" (first run) or "last session did A, B" (resumption).
  4. Negotiate cadence — asks "all at once, or check in after a piece?" and may propose a breakpoint. Decided per session; never persisted.
  5. Execute to the agreed cadence. linear only Before writing any code, advances the ticket to In Progress (fallback: the team's first started-type state), resolved by name via list_issue_statuses; never blocks coding on a status change. File host has no status.
  6. Amend when reality diverges — invokes the amend skill instead of silently working outside the contract.
  7. Verify against Done when — before declaring done, dispatches the contract-verifier agent, which runs each Done when bullet and returns a per-bullet verdict (met / not met / drifted / unverifiable) with evidence. Verification is behavioral, not a diff-read — drift is plausible code that reads right but doesn't do what was promised. Inline /verify is the fallback if the agent is unavailable.
  8. End — when scope ships and the Done-when checks pass, prompts the user to run /spec-flow close. Does not auto-close.

The Out-of-scope fence holds here. If a tempting addition surfaces during implementation, the skill must propose an amendment — it may not just add it.

Mid-stream — amend sign-off required

Proposes a contract edit when the work reveals the contract is becoming inaccurate. Usually invoked from within implement, not directly by the user. The load-bearing rule: it never edits the contract silently.

  1. Summarize the divergence in one short paragraph — what drifted and why.
  2. Propose the specific edit as before/after, scoped only to the affected section(s).
  3. Wait for sign-off — "yes" applies the AI's version; a modified edit applies the user's version; "no" leaves the contract untouched and forces reconciliation within it.
  4. Apply to the host (Edit for files; get_issue + save_issue for Linear, preserving untouched sections).
  5. Resume implementation. The amendment is now part of the agreement.

Triggers on: wrong approach, a new constraint, a scope shift, or a resolved open question worth promoting to Approach. Not for trivial details (variable names, helper choices). Frequent amendments are flagged as a signal the original drafting was thin.

Phase 3 — close migrate to durable layer

Ends an active contract by migrating durable findings out of the ephemeral contract and into the durable layer, then archiving. Closing implies completion — it is not for pausing or abandoning.

  1. Identify target & detect host.
  2. Read contract + actual change — detects the VCS first (.jj/ present → jj log / jj diff, else git log / git diff) and surveys what shipped since the contract was created; compares Approach against the code.
  3. Done-when check (first gate) — walks each Done when bullet: met / not met / drifted. Prefers behavioral confirmation over diff-reading — reuses implement's verify result if it ran this session, otherwise dispatches the contract-verifier agent (Done-when bullets + diff scope + detected VCS) to run the checks now in isolated context, falling back to inline /verify. If any bullet is not met, it halts and asks (close anyway as a known gap, amend to a narrower done, or pause). It will not silently archive an unmet contract.
  4. Offer a drift check (optional) — if ndr atoms exist for the repo, prompts once to run ndr:drift-check against the diff. Opt-in, never auto.
  5. Propose migrations — ndr atoms via /capture-decision for real architectural choices; README updates for user-facing changes; an explicit "not migrated" list (out-of-scope items, resolved open questions, conversation history).
  6. Sign-off + apply — migrations are AI-proposed, applied only after approval. If any fails, it halts before archiving.
  7. Archive (host-aware) — see the state view below.
  8. Confirm with a short host-specific summary.

Where the contract lives at each phase

The contract is born ephemeral and ends archived. What happens at close depends on host: a file moves and flips a frontmatter field; a Linear ticket's body is left intact while its state advances to a review state — spec-flow never sets a completed state (Done/Closed), which stays the human's call at merge.

Closing is non-destructive in both hosts: the file is archived, not deleted; the ticket body is preserved. spec-flow advances Linear state through the lifecycle (start → Contract Review, implement → In Progress, close → a review state) but never sets Done/Closed — the merge flip stays the user's call.
