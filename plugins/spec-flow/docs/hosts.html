spec-flow / the two hosts

The two contract hosts

The same five-section contract lives in one of two places. The host changes where the body is read and written — and what happens to it at close — but never the contract's shape.

file (default)

  • .docs/YYYY-MM-DD-<slug>.md in the working repo.
  • Has YAML frontmatter (status, topic, started).
  • Enumerable — start/implement/close can scan .docs/ for active contracts.
  • At close: moved to .docs/archive/.

linear

  • An existing Linear issue (e.g. CAR-49); its description holds the body.
  • No frontmatter — the ticket's own metadata is the workflow signal.
  • Not enumerable cheaply — you name the ticket explicitly.
  • At close: ticket left untouched; you flip its state yourself.

The host is not persisted. Every skill re-detects it from the identifier each time (or from the goal text, at start) — the same no-stored-flag model as cadence.

How host detection works

Detection differs by phase because the input differs. At start the user types a free-form goal, so phrasing matters. At implement/amend/close the user passes an identifier, so only its shape matters.

The ambiguous escape is a single question: "Use CAR-49 itself as the contract, or draft a .docs/ file that references CAR-49?" — then the user's answer is used.

At implement, amend, close — shape only

No phrasing analysis at these stages. The identifier shape is the whole signal:

IdentifierHost
Matches ^[A-Z]{2,5}-\d+$ (e.g. CAR-49)linear
Anything else (kebab slug, filename)file

Linear MCP availability is a gate

Every Linear-host action requires the mcp__linear-server__* tools to be loaded. If they aren't, the skill surfaces the fact and offers a choice — identical wording across all four skills:

"Linear MCP server isn't connected — I can't read or write CAR-49.
 Fall back to a .docs/ file contract, or pause while you wire up the MCP yourself?"

It never connects the MCP for you. No claude mcp add, no paste-and-go command — connecting MCP servers is treated as a user decision. The skill waits.

What is explicitly not spec-flow's job

spec-flow owns the contract lifecycle and only the contract body. For the Linear host it does not own:

  • Linear title conventions.
  • Required fields at ticket creation (team, priority, labels).
  • Linear status flow — which state means what, and when to transition.
  • PR-to-ticket linking expectations.
  • The decision of when to open a Linear ticket vs. a .docs/ file.

Those belong to the broader Linear workflow (the sibling linear plugin). spec-flow assumes a ticket already exists; it only writes and reads the contract body.

Documented-but-unbuilt host shapes

The hosts.md reference records two future shapes that are not implemented, kept on file so the design intent is visible:

  • Linear-new (Shape B) — start could create a new ticket (prompting for title/team/status) rather than only attaching to an existing one. Deferred until Linear-side defaults settle.
  • GitHub Issues (Shape C) — same adapter pattern, detected by issue-URL or owner/repo#NN shape, with the same suggestion-only close behavior. Out of scope for now.
